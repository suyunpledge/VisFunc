# VisFunc 现状问题与优化方案（2026-11-27）

给 Codex 的执行文档。前半部分是问题诊断，后半部分是分阶段任务，每个阶段写明做什么、怎么验收、不要做什么。**阶段 1、2 的结论可能改变后面阶段的优先级**，做完请先把结果交给用户看，再继续。

---

## 一、现状：一个仓库，四个方向

| 方向 | 代码位置 | 主要开发时间 | 和 README 主张的关系 |
|---|---|---|---|
| VisFunc-Image：图片编译成像素、区域、轮廓等可查询函数，并核对模型结论 | `svsg/` | 9 月起 | 核心 |
| VisFunc-Motion：从录屏或 Qt 属性测出界面动效 | `packages/motionspec/` | 11-16 起 | 核心，目前最主要的研究结论都来自这里 |
| 识别：行人（MOT17/MOT20）、COCO8 物体、字幕 OCR、播放器图标 | `svsg/recognition/`、`bench/pedestrian_*`、`bench/*overlay*` | 11-20 到 11-22 | 边缘 |
| 桌面 Agent MCP：等界面稳定、按名字或文字点击、动作回执、屏幕历史 | `packages/motionspec/motionspec/agent.py`（1,708 行，全仓最大的文件）、`action_receipts.py`、`screen_history.py`、`settle.py` | 11-22 到 11-26 | 另一个产品。Keystone 已把它作为 vendored 依赖接入 |

README 的定位是「在本地测量图片和界面动效，为 AI 提供可查询、可核对的数值证据」。最近一周的投入几乎全在第四行。

README 已经如实写了不少局限：9 个较难场景在开发中反复用过、不算独立验证；场景由 Qt 逐帧渲染，真实录屏验证很少；布局重排会测错一百多像素。下面的诊断在此基础上展开。

## 二、主要问题

### P1　核心对照的「只给视频」基线在结构上就看不清

- 片段长 0.6–0.8 秒。MiMo 按接口上限每秒抽 10 帧，豆包每秒 5 帧，GPT 拿到的是 8 张间隔 100 ms 的静帧。模型实际只看到 3–8 帧。
- 判分要求起点误差在 ±34 ms（两帧）以内，时长误差在 ±15% 以内。以这个采样率，模型在物理上就做不到。
- 所以「只给视频 55–58%，加测量 82–92%」证明的主要是「看不清」和「直接给了答案」之间的差距，不能说明 VisFunc 比其他做法好。
- **缺少两个强基线：**
  - **密集帧**：在相同的 token 预算内，给模型尽可能多的带时间戳的帧或裁剪图；
  - **模型自己写代码量**：给模型视频文件和一个 Python + OpenCV 沙盒，让它自己测。这才是 VisFunc 在现实中真正的竞争对手。

### P2　端到端分数基本等于分析器本身的准确率，而分析器还没有独立的测试集

- 9 个较难场景上，分析器本身的逐项正确率是 85%，模型加上测量结果后是 82%。模型基本只是把测量结果转述出来。
- 也就是说，**瓶颈在分析器**。分析器对真值的准确率可以不调用任何模型直接测，几乎不花钱，但目前没有固定的留出集。较难的 9 个场景已经在开发中反复使用过。
- 已知的系统性错误：布局重排时把尺寸变化测成位移（偏差可达一百多像素）；H.264 的色度抽样会抹平颜色过渡。

### P3　「可查询函数」这种形式的价值还没被证明

- 11-17 的纯参数复测（`docs/timing-protocol-retest-20261117.md`）：新纯参数 145/147，共享时间计算的文字摘要 147/147。
- 起作用的是测量结果本身，不是「函数」这个载体。README 把「可查询函数」作为核心卖点，这一点目前没有证据支撑。和 HR 项目里「分级」的问题是同一类。

### P4　数据几乎全是合成的，样本量也小

- 场景都是 Qt 逐帧渲染，帧间隔严格均匀。真实录屏会丢帧、有录制延迟、帧率可变，这些情况验证很少。
- 6 个模型、6+9 个场景、每种条件 216 次调用，按逐项计分。同一场景内的各项高度相关，有效样本接近场景数，而不是项数。没有按场景计分，也没有置信区间。
- GPT 组织没开通视频输入，GPT 的「只给视频」组用的是静帧，不能代表它的原生视频能力。

### P5　识别方向的投入回报低，而且偏离核心

- COCO8（8 张图、30 个目标）：多视图复核后误报 9→2，但漏检 10→16，召回变差了。
- MOT20：重遮挡行人多找回 3 个（514→517，共 740 个标注）。
- 字幕和图标规则是按播放器底栏调出来的，README 自己也写了：用在普通界面上会把前进箭头报成播放键。
- 这些工作既不支撑「给 AI 提供界面数值证据」的主张，也没有达到能单独拿出来的水平。

### P6　桌面 Agent：功能扎实，但有安全缺口，也没有外部基准

- **提示注入通道**：`read_screen_text`、`find_on_screen`、`read_screen_history` 把屏幕上的文字原样交给 Agent，没有标明这是不可信内容。网页或文档里写着「请点击删除」，Agent 收到的就是一段普通文字。允许规则只能限制「能操作哪个窗口」，限制不了「在允许的窗口里点什么」。
- **测试都是自建的**：Keystone 16/16、4/4、换位场景 4/4，测试窗口是为目标问题专门造的。没有跑过 ScreenSpot、WindowsAgentArena 这类公开基准，也没有和 Keystone 自带的窗口驱动在同一批任务上比过成功率。
- **已知缺口**：最后一次复核和系统真正收到点击之间仍有时间差；Chrome 的 UI Automation 没验证；浏览器里只有图标的按钮找不到；本机 ESET 会挡住浏览器截图。
- **架构**：桌面 Agent 和动效测量无关，却放在 `motionspec` 包里，而且已经是全仓最大的文件。

### P7　工程卫生

- `main` 上有一批没提交的改动（点击复核：`agent.py`、`test_agent.py`、`agent_canvas_app.py`、两份 README，以及新的评测脚本、结果和文档）。
- 评测结果一部分在 `docs/`，一部分在 `packages/motionspec/bench/results/`；`bench/` 下有 37 个脚本，没有统一入口和固定的数据划分。
- `svsg/` 下 9 月的分层模块（`l1_compiler`、`l15_verifier`、`l2_runtime`、`l3_orchestrator`）现在还有多少在真正使用，需要核实。
- 完整部署包 917 MB（解压 2.3 GB），桌面精简包 156 MB。

## 三、优化方案

### 阶段 0　收尾与整理（先做）

1. **先处理 `main` 上没提交的点击复核改动。** 这是 Codex 自己做到一半的工作：跑完测试，确认 `docs/agent-click-recheck-20261126.md` 的结论和代码一致，单独提交。不要和本方案的其他改动混在同一个提交里。
2. 评测结果统一放到 `bench/results/<日期>-<名称>/`，`docs/` 只放说明文档，修正所有相对链接。
3. 核实 `svsg/l1_compiler`、`l15_verifier`、`l2_runtime`、`l3_orchestrator` 的调用情况。没有被 API、CLI 或测试之外的代码用到的，列一张清单交给用户，先不要删。
4. 全部测试通过后提交。**推送前先问用户。**

### 阶段 1　分析器独立评测（不调用模型，最便宜，也最关键）

1. **合成数据的留出集**：在 `packages/motionspec/tools/qt_scenes.py` 的基础上做参数化生成器，按固定种子随机化元素位置、距离、时长、缓动、多个动效重叠和布局重排，生成至少 60 个场景。`dev` 和 `test` 各一半，写进 `bench/splits.json`。现有的 6 个基础场景和 9 个较难场景全部归入 `dev`。
2. **真实浏览器录屏，并自动取得真值**：
   - 用一组本地 HTML 页面，包含 CSS transition、CSS animation、Web Animations API，以及会引起布局重排的展开面板、侧栏收起、列表插入；
   - 真值来自浏览器本身：通过 Chrome DevTools Protocol 的 Animation 域，加上页面内 `requestAnimationFrame` 每帧记录 `getBoundingClientRect()` 和计算样式；
   - 用 ffmpeg 的 `gdigrab` 或 CDP 的 screencast 录屏，保留真实的丢帧、可变帧率和压缩；
   - 每段视频和真值来自同一次采集，并记录两者的时钟对齐方式。
3. **指标**：逐字段的误差分布（起点 ms、时长、距离 px、方向、缓动类别），按场景汇总，附按场景重抽样的 95% 置信区间。把「格式失败」「测错」「漏测」分开统计。
4. 统一入口 `bench/analyzer_eval.py --split dev|test --source qt|browser`。

验收：同一份代码连续跑两次，结果一致；报告里有合成和真实浏览器两组的场景级指标和区间。这一步不花 API 费用。

### 阶段 2　强基线对照（调用模型）

在阶段 1 的 `test` 上（合成和浏览器各取一部分），比较以下条件：

| 编号 | 条件 | 说明 |
|---|---|---|
| V0 | 只给视频（现状） | 沿用各接口的上限抽帧，作为历史可比项 |
| V1 | 密集帧 | 在与 V3 相近的输入 token 预算内，给尽可能多的带时间戳的帧（可以裁到变化区域） |
| V2 | 模型自己写代码 | 给视频文件和一个本地 Python + OpenCV 沙盒，限制步数和时长，让模型自己测 |
| V3 | 视频 + 文字摘要 | motionspec 的测量结果写成纯文字 |
| V4 | 视频 + 可查询函数 | 通过工具调用查询 `functions.json` |
| V5 | 视频 + Qt 探针 | 只在 Qt 场景上有，单列 |

- 模型：至少 3 个，尽量包括能输入原生视频的模型（MiMo、豆包）。GPT 仍用静帧时要标明。
- 指标：场景级正确率和置信区间；每题的输入和输出 token、费用、耗时；格式失败单列。
- 费用：先估算，**超过 8 美元先问用户**。V2 的沙盒必须在本机隔离目录里运行，不能联网，不能访问项目以外的文件。

这一步的结论会决定后面怎么走：
- **V3 ≈ V4**：「可查询函数」不是卖点。README 改为以「测量结果」为核心，函数查询作为可选的高级接口。
- **V2 接近 V3**：VisFunc 的价值要改用速度、费用、稳定性来证明，必须把这三项测出来写进结论。
- **V1 明显好于 V0**：README 里「只给视频」的基线要换成 V1，旧数字只作为历史记录保留。

### 阶段 3　分析器改进：针对已知的系统性错误

每一项都必须在阶段 1 的 `test` 上验收，不能只在 `dev` 上看效果。

1. **布局重排**：分别跟踪元素的上、下、左、右四条边，四条边位移不一致时判为尺寸变化，一致时才判为平移。这样「面板展开推下方元素」和「侧栏收起拉动内容」就能和真正的位移区分开。
2. **真实录屏的时间**：用容器里的 PTS 作为帧时间，不要假设帧率恒定。检测丢帧和重复帧，在结果里标出可信度。
3. **压缩视频里的颜色**：颜色过渡先在亮度通道上检测，色度变化给出低可信度标记，不要输出看起来很精确的数值。
4. 每项改进都要能用开关关掉，并在报告里同时列出开关前后的场景级结果。

### 阶段 4　桌面 Agent：先补安全，再上公开基准

1. **标记不可信内容**（优先级最高）：所有从屏幕取得的文字（OCR、UI Automation 名称、屏幕历史里的提示文字），在 MCP 结果里放进单独的字段，并加上 `_meta` 标记，例如 `"visfunc/untrusted_content": true`。同时在 README 和工具描述里写明：客户端不应把这些文字当作指令。
2. **危险操作二次确认**（可选，默认开启）：目标标签匹配「删除、移除、发送、提交、付款、Delete、Remove、Send、Submit、Pay」等词时，需要调用方显式传 `confirm_destructive=true`，否则返回 `not_started`。规则做成可配置的列表。
3. **点击后核验**：派发后用 `screen_history` 检查目标标签区域是否出现了预期的变化，结果写进回执（`post_check: changed | unchanged | unknown`）。这样「复核到派发之间的时间差」引起的误点至少能被发现。
4. **公开基准**：
   - **定位能力**：从 ScreenSpot-v2 或 ScreenSpot-Pro 里挑出目标带可见文字的样本，离线测 `find_on_screen` 的 OCR 路径，不需要调用模型；
   - **端到端任务**：从 WindowsAgentArena 里挑 20–30 个任务（记事本、设置、文件资源管理器、Edge），在同一批任务上比较「Keystone 自带窗口驱动」和「Keystone + VisFunc」的成功率、步数、token 和耗时。这一项需要虚拟机环境，开始前先估算准备工作量和费用，交给用户决定。
5. **Chrome 无障碍树**：用 `--force-renderer-accessibility` 启动 Chrome，验证 UI Automation 能否找到浏览器里只有图标的按钮。

验收：不可信标记有单元测试覆盖；公开基准的结果和自建测试的结果分开列出。

### 阶段 5　范围收口与架构

1. **桌面 Agent 拆成独立的包**，例如 `packages/visfunc-desktop/`，依赖 `motionspec` 的 `settle` 和屏幕历史。保留 `motionspec agent-mcp` 命令作为兼容别名，至少保留一个版本。拆分前先列出 Keystone 的 vendored 代码引用了哪些模块路径，交给用户确认怎么同步。**不要直接改 Keystone 仓库。**
2. **识别方向移到 `experimental/`**：行人、COCO8、播放器图标、字幕规则保持可运行，在 README 里移到单独的「实验功能」一节，并写明局限。在它们能直接支撑核心主张之前，不再继续投入。
3. **README 重写结构**：
   - 第一屏只放核心主张，以及阶段 2 的强基线对照结果（包括对 VisFunc 不利的条件）；
   - 「研究结论」和「产品功能」分成两节，桌面 Agent 归到产品功能；
   - 「结果汇总」表里的每一行都标明数据是合成的还是真实的，属于 dev 还是 test。
4. 清理阶段 0 列出的无用旧模块（等用户确认后）。

### 阶段 6　发布

1. 只从打了 tag 的干净提交打包，部署包里写入提交哈希和依赖锁定文件。
2. 精简包在现有 156 MB 的基础上，检查 OCR 模型、Qt 和 OpenCV 有没有重复携带。
3. 发布前跑完阶段 1 的分析器评测和阶段 4 的安全测试，结果附在发布说明里。
