# 时间协议统一与独立会话复测（2026-11-17）

协议修复缩小了纯参数与文字摘要的差距，但没有完全补齐。MiMo Flash 的列表时长错误得到修正，卡片场景仍持续选择可见时间；GPT Sol 本轮旧、新参数均满分，不能把历史分数变化归因于改动。

## 协议改动

- `timing.visible_change`：检测到变化的区间。原有顶层 `t_start_ms/t_end_ms` 保留此含义。
- `timing.estimated_design`：命名曲线对齐得到的设计时间估计，明确 `is_ground_truth=false`。
- 保存 `basis_t_start_ms`、`start_shift_ms`、`duration_ms`、`rmse`，起止值可复算；通道各自保留时间证据。
- 没有可靠拟合、缺少对齐、片段截断或估计起点早于零时返回 null 和原因，不能回退为可见时长。
- `motionspec.timing.motion_timing()` 是唯一计算入口；像素/Qt 规格、旧规格升级、摘要共用它。SVSG 编译器只读取并校验物化后的结果，依赖方向保持 MotionSpec → SVSG。
- SVSG 旧函数包继续可读；直接编译未升级的旧片段标记 `legacy_missing_timing`。设计区间不会扩大原有采样/拟合函数的可求值范围。

## 复测设计

仍使用上一轮两段 UI 视频的同一份 40fps 像素测量：没有重新采样、调整拟合算法或读取真值生成参数。旧、新参数的唯一差异是 `segments[].functions.timing`；自动检查删除该字段后数据完全一致。

MiMo Flash（Token Plan）和 GPT-6.1 Sol，各 2 段 × 3 条件 × 3 次重复，共 36 次请求。三个条件为旧纯参数、新纯参数、共享时间计算的文字摘要。全部无图片、无视频、无历史；相同片段的问题文本完全相同。输出上限 1800，无自动重试，调用计划和输入 SHA 在运行前冻结。

36 次请求中 33 次成功；3 次 MiMo 旧参数请求发生 SSL EOF，实际用量未知。它们属于传输失败，原始响应及耗时全部保留，未替换成成功重跑。

## 补上了什么，还差什么

- MiMo Flash 的列表片段：旧参数成功的两次均 16/19，新参数三次均 19/19。原先将可见时长 225/250ms 当设计时长，新增字段提供共享计算的 275ms 拟合估计。真值 300ms，在原定 ±15%/至少 25ms 容差内，因此判正确；这不代表估计等于真值。
- MiMo Flash 的卡片片段：新参数三次仍为 11/13，继续回答起点 325ms、时长 450ms，而协议明确提供设计起点 250ms、时长 600ms。这里是模型选错语义字段，不是后台算不出设计时间。
- GPT Sol 的旧参数、新参数、摘要在本轮各为 96/96。上一轮纯参数 29/32 的差异可涉及模型输出波动，本轮没有观察到 GPT 的配对提升。
- 新纯参数合计 186/192，摘要 192/192，剩余六项错误全部来自 MiMo 的上述卡片起点/时长，在三个重复中复现。全部新参数的完整对象正确率为 27/30，完整响应正确率为 9/12。
- 接下来若继续改读取层，应优先减少兼容别名和原始通道数据对模型的干扰，或让明确的时间查询交给程序选择对应字段；不能在评分脚本里把错误答案替换为协议值。
