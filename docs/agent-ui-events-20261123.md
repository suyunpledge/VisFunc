# 桌面动作重试、界面事件缓存与会话用量

桌面 Agent 在 Windows 目标窗口执行动作后，会在等待界面稳定时开始记录变化。模型思考期间出现又消失的提示，可以从动作回执中的 `screen_history.history_id` 找回。客户端断线时，可用原操作标识取回执行状态。

## 客户端怎样重试动作

为每次有意点击或输入生成一个 UUID，并在首次发送前和待执行步骤放在一起。重发同一步使用原 UUID，再执行一次相同点击则分配新 UUID。HTTP 客户端可用 `Idempotency-Key` 请求头，HTTP 和 stdio 客户端也可以使用下列 MCP 元数据。模型工具定义无需携带 UUID。

```json
{
  "jsonrpc": "2.0",
  "id": 19,
  "method": "tools/call",
  "params": {
    "name": "click_point",
    "arguments": {"window_title": "My app", "x": 200, "y": 140},
    "_meta": {"visfunc/operationId": "ff498329-cb77-47df-ab9f-3d4d049de5f3"}
  }
}
```

已初始化的 HTTP 会话可用同一个 `Mcp-Session-Id` 和 JSON-RPC 请求编号重试。stdio 的请求编号在当前连接中有效。重新建会话或更换请求编号时，要沿用显式操作 UUID。无会话且无 UUID 的 HTTP 写调用会在派发前返回错误。

服务先把操作标识和参数摘要写入 SQLite，再执行动作。已完成的重复请求返回 `replayed=true` 和原执行状态。相同标识配不同参数会报冲突。如果进程在预留操作与写完回执之间退出，重试会返回 `execution_state=unknown`，此时应只读检查窗口。应用本身与 SQLite 分属两个系统，这个区间的实际执行结果可能需要人工确认。

默认回执库为 Windows 当前用户的 `%LOCALAPPDATA%/VisFunc/action-receipts.sqlite3`，可用 `VISFUNC_ACTION_DB` 选择部署实例的持久路径。服务器重启后继续使用同一文件。每个标识自首次预留起有效 24 小时，过期行在下一次动作预留时清理。上限为五万条，有效回执占满或存储不可写时，新动作会在执行前停止。输入字段原文和画面只用于处理或观察，回执库仅保存标识、参数摘要、有效期和简短状态。

## 按需读取界面事件

- 默认按目标窗口采样 20 秒。像素最高 8 Hz，Windows UI Automation 控件最高 4 Hz。可读取控件出现与消失、字段或开关变化、匹配窗口切换，以及像素变化区域。纯控件路径也可用于已识别为屏幕捕获受限的窗口。
- 首次读取使用 `read_screen_history(history_id=…, compact=true)`。需要读自绘内容时加 `read_text=true`。每次至多识别两份选中的像素裁图，同一事件的成功 OCR 结果（含空结果）可复用，OCR 异常留待后续重试。
- 后续读取传 `after=next_after`。同一筛选条件下，`has_more=true` 表示还有下一页。`missed_events` 表示游标与尚存的最早记录之间有缺口。可按屏幕区域筛选。控件按中心点匹配，像素变化按矩形相交匹配。
- 简表每页最多 12 个事件，事件条目的 UTF-8 JSON 预算为 3,000 字节。普通多事件页的预算为 12,000 字节。逐条详情用 `event_id` 且关闭 `compact`。单次控件采样最多保存 12 项变化，每个文本字段最多 160 个字符。默认返回文字，图片须在允许图像的服务上按事件单独请求。预算口径排除了外层协议和单独请求的图片。实际模型用量取自提供商逐轮 usage。
- 同时最多保留四个窗口记录，每个记录的裁图上限为 4 MiB。超过容量会释放较早记录，录制开始后经过采样时长加 60 秒会释放整个记录。同一目标的下一次动作会停止上一段采样。`--history-seconds 0` 可关闭事件录制。重启后，原动作回执仍可查询，内存中的控件事件和裁图已经释放。
- 运维客户端可发送 MCP `ping` 并指定 `params._meta["visfunc/cacheStats"]=true`。进程级计数包含事件查询数、返回事件的查询数、已失效句柄查询数、OCR 实算与复用次数、动作预留、重放及标识冲突次数。无新事件的正常增量查询也计入查询总数。判断是否命中任务所需信息，还要核对实际事件内容。

## 本机独立会话对照

在本机 Keystone 使用 GPT-6.1 Sol，每个会话只操作一个置顶 Qt 测试窗口。点一次 Start check，收到动作回执后，窗口显示随机五位码 625 毫秒再恢复。以应用记录的号码、模型最终回答和实际点击计数核对。基线为 `92cf3e1`。运行顺序为旧 A、新 A、新 B、旧 B，工具权限、任务指令和模型一致，窗口标识和随机号码各自独立。

| 条件 | 提示码与回答 | 实际点击 | 首次查询含真值 | 工具调用 | 输入 token | 输出 token | 总 token | 会话耗时 |
| --- | --- | ---: | --- | ---: | ---: | ---: | ---: | ---: |
| 旧 A | 34401 | 1 | 否，第二次查询命中 | 4 | 10,514 | 233 | 10,747 | 31.4 秒 |
| 新 A | 40977 | 1 | 是 | 3 | 6,255 | 180 | 6,435 | 39.7 秒 |
| 新 B | 55468 | 1 | 是 | 3 | 6,254 | 178 | 6,432 | 42.8 秒 |
| 旧 B | 34161 | 1 | 是 | 3 | 7,534 | 168 | 7,702 | 16.6 秒 |

两组最终都答对 2/2。旧版首次查询命中任务所需信息 1/2，新版为 2/2。新版两次都在控件变化和像素 OCR 中找到了真值。两次都首次读取裁图，合计实际 OCR 4 次，复用 0 次。

按两次完整会话求和，模型总 token 从 18,449 降至 12,867，减少 30.3%。输入用量包含提供商报告的缓存输入 token。按输入 token 加权，提供商前缀缓存占比为旧版 14,193/18,048（78.6%），新版 9,307/12,509（74.4%）。工具说明缩短、回执序列化和旧 A 的额外一轮都影响总量。相同三次工具调用的旧 B 与新 B 分别消耗 7,702 和 6,432 token。两组平均耗时分别为 24.0 秒和 41.3 秒。每组仅两次，耗时包含网关和模型响应时间。

仓库内的基准入口又运行一次独立会话，返回 11434，一次点击、三次工具调用、6,425 token。包含这次单独核验在内，本轮五次付费会话共用 37,741 token。可通过以下命令复测，结果 JSON 保存逐轮用量、提供商缓存输入和窗口终态。

```powershell
python packages/motionspec/bench/agent_keystone_live.py KEYSTONE_REPO QT_PYTHON result.json --models gpt-6.1-sol --tasks pulse --max-turns 9
```

## 断线、重启与重复读取

另用真实 HTTP MCP 操作 Qt 窗口。客户端发送点击后直接关闭连接，再用同一 UUID 取回回执。随后终止并重启服务，换请求编号重发相同 UUID，应用实际点击数仍为 1。为相同坐标分配新 UUID 后，点击数变为 2。

同一窗口的纯控件事件找回了已消失的提示 37716。对同一批裁图，第一次读文本实算 2 次，第二次复用 2/2，新增 OCR 调用为零。4 次历史查询中 3 次返回事件，另 1 次使用末尾游标，正确返回空页。整个故障注入与重复读取过程使用本地程序驱动，没有模型 token 消耗。

这些实测覆盖了有可访问性文字的 Qt 窗口。发生在采样间隔内、没有留下像素或控件证据的变化仍可能漏记。针对自绘画布、不同应用或长任务，首次命中率、用量和延迟需要分别测量。[逐会话用量、工具调用、窗口终态和故障注入结果](../packages/motionspec/bench/results/agent-ui-events-20261123.json)
