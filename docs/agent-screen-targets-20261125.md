# Keystone 实际桌面操作对照

在 Windows 上分别用提交 `a8cbff9` 和加入 `click_text` 的源码运行桌面 MCP。Keystone 的 GPT-6.1 Sol 通过相同的已认证 HTTP 测试入口完成任务，每次重建会话和目标窗口。两个版本都使用同一份任务指令、工具范围、14 轮上限和验收程序。测试只向模型提供 MCP 的文字结果。服务能在本机读取像素、做 OCR 和派发点击。模型回答、窗口实际收到的操作和逐轮用量分别记录。

自绘任务要求选中 High、打开 Notify team、点击 Confirm 并报告最终状态。压力场景在第一次操作派发前交换 High 和 Medium 的位置。两组使用相同触发时机，第二对反转版本顺序。基线两次都点中了错误的有效按钮，随后通过再次读屏纠正。空白处点击计数为零，因此误点按应用记录的按钮名称判断。新版两次均按正确顺序操作。按钮换位场景的总 token 从 44,082 降到 27,424，下降 37.8%。

固定布局里，两版都用了两次观察和三次点击。Windows 原生打开文件对话框中，两版都用 UI Automation 选择了 `report-final.txt`。验收读取对话框实际接受的文件路径和次数，窗口使用 Windows 对话框类 `#32770`。这两项任务的新版调用次数与基线相同，token 和耗时均略有增加。附加工具定义会占用上下文。

四个会话合计，基线用量为 68,802 token，新版为 53,157 token。两组最终均完成 4/4。这里的总量为提供商每轮输入与输出之和，含缓存输入。两组只在一个指定的排版变化场景各重复了两次，结果适用于判断这个具体问题。各任务的模型回答、工具轨迹、屏幕坐标、实际选中状态和缓存输入用量见逐会话记录。[原始测量](../bench/results/20261125-agent-screen-targets/agent-screen-targets-20261125.json)

## 点击如何复核

`click_text(window_title, text)` 对操作前的画面做一次完整 OCR，按已有规则忽略大小写和空白，查找完整文字标签或连续词组。必须恰好命中一处且通过 OCR 置信度检查。临派发前再次抓帧，复核窗口范围和标签区域的像素。坐标消息只投递给目标顶层窗口及其子控件，同一程序的其他顶层窗口覆盖目标位置时会拒绝点击。

拒绝派发会返回 `execution_state=not_started` 和下一步观察建议，MCP 标记工具错误。已派发后观察失败仍返回实际执行状态。动作回执延续原有操作标识去重行为。成功回执附识别文字、边框、分数及物理屏幕点击点。连续变化的目标可能被拒绝。最后一帧与系统接收输入之间仍存在时间间隔。

## 复测

在已登录的 Windows 桌面运行下列命令。程序为本次 MCP 创建临时令牌，只允许测试窗口，模型仅可调用此次注册的屏幕工具。文件选择器使用临时文件，不会打开用户文档。

```powershell
python packages/motionspec/bench/agent_keystone_live.py KEYSTONE_REPO QT_PYTHON out.json --models gpt-6.1-sol --max-turns 14 --tasks canvas_reflow canvas file_dialog
```

基线比较使用同样的测试驱动，并让 MCP 子进程导入基线检出的服务代码。
